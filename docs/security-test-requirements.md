# 情報漏えいを重点とするローカルセキュリティ検証の要件

調査日: 2026-10-14。対象コード: bda5250。
今回の作業はソースと公式資料の調査のみ。仮想攻撃・負荷試験・公開サイトへの検証リクエストは未実施。

## 重点とする目的

作者・閲覧者の個人情報、認証情報、非公開資料が、配信ファイル、Git公開、API応答、外部通信を通して漏れないかを最優先に確認する。負荷耐性やカウンターの不正加算は補助項目へ下げる。

公開サイトの診断とGitリポジトリの診断は分ける。`dist/` の外に退避しても、公開リポジトリにコミットすればGit経由で閲覧できる。現在のリポジトリ公開設定や過去デプロイの到達性は未確認で、ローカル調査だけでは確定しない。

| 分類 | 主な確認対象 | 判定の考え方 |
| --- | --- | --- |
| 作者の個人情報 | 実名、私用メール、住所、電話番号、端末ユーザー名、絶対パス、Git作者情報、画像メタデータ・写り込み | 公開用Xアカウントや署名と、意図しない個人情報を分ける。本人の公開意図が不明なら確認候補とする |
| 認証・接続情報 | APIトークン、秘密鍵、パスワード、認証Cookie、接続文字列、Webhookの秘密値 | 値の使用や外部サービスへの有効性照会はしない。単なる公開識別子・DB名と認証能力のある秘密を区別する |
| 内部資料 | `.env`、設定、ログ、DB、バックアップ、元資料、未公開画像、ソースマップ、生成物 | HTTPの公開範囲とGit追跡・履歴の両方を確認。本文が取得できたことをもって漏えいを判定する |
| 閲覧者の保存情報 | 素材数、編成、所持武器などのlocalStorage | 通常操作・不正入力で外部へ送られないか。個人情報そのものか、利用状況データかも区別する |
| サーバー情報 | API成功・失敗応答、例外、DB内容、IPやヘッダーの記録 | 本番の実ログを取得せず、ローカルのダミー情報で応答とログを検証する |

## 最優先の調査手順

1. `dist/`、Functions、追跡ファイル、関連する未追跡ファイルを棚卸しする。ユーザーのホーム全体や認証保管庫を探索しない。
2. 現在のファイルとローカルに存在するGit履歴・参照を対象に、秘密情報らしい形式、メール、絶対パス、コメント、設定値を検出する。Git作者・コミッター情報と履歴中の削除済みファイルも対象とする。履歴を取得するためのfetchは行わない。
3. 検出結果はルール名・ファイル・行・コミットと伏せ字だけを出す。誤検知を確認し、実値・一致行をコマンド出力やコミットする報告書へ転載しない。
4. 現在残っている画像と退避画像のメタデータを確認する。画面内のユーザー名・通知等の写り込みも確認する。単にファイルを開いただけでは全メタデータの確認済みとしない。
5. `fetch`、XHR、sendBeacon、WebSocket、外部script、iframe、リンク、画像URL等を棚卸しし、送信先と送信され得る内容を整理する。外部scriptは同一ページの権限で動くことと、別Originのiframeを区別する。
6. 専用環境のlocalStorageに識別用の架空値を入れ、外部送信を遮断した状態で通信試行を記録する。架空値がURL・本文・ヘッダー等に混入しないか確認する。第三者サービスの本物のスクリプトを試験中に取得・実行しないため、その内部挙動は未検証とする。
7. ローカルHTTPで公開範囲外へのアクセスとAPI障害応答を確認する。テスト用の秘密マーカー以外の実秘密は配置しない。
8. 検出項目を「意図された公開情報」「非公開のままの情報」「漏えい候補」「再現した漏えい」に分類する。実際に共有済みの秘密が判明した場合は失効・再発行の必要性を報告し、勝手に履歴書換えや認証情報の変更は行わない。

第1段階のファイル・Git・通信経路調査には仮想サーバーもWranglerも不要。サーバー準備はHTTP応答の確認段階で行う。

## 対象と構成

- 配信対象は `dist/`。静的HTML・CSS・JavaScript主体。
- サーバー処理は `functions/api/home-view.js` のPOST API。HOME閲覧時にD1の `page_views` を更新する。
- `dist/_routes.json` は `/api/*` のみFunctionsを起動する設定。
- 素材管理、成長率、武器管理等はブラウザのlocalStorageに保存する。
- ログイン、決済、ファイルアップロード、利用者向け管理APIは今回読んだコードでは見当たらない。
- 検証記録ページはXの外部スクリプトとYouTubeのiframeを読み込む。リンク先サービス自体は検証対象外。
- 非表示にしたスクリーンショットは `source-assets/` に保管されている。公開対象外であることも確認する。

## 必要な環境

1. 本番リポジトリを変更しない検証専用コピー。起動時にGitコミットと差分を記録する。
2. WranglerのローカルPages実行環境と、空のローカルD1。単なる静的HTTPサーバーだけではAPIを検証できない。
3. `schema.sql` だけで初期化したダミーDB。実データ、Cloudflareログイン、APIトークン、本番DB IDは不要。
4. 設定は検証コピー内に限定し、D1バインディング名 `COUNTER_DB` をローカルDBへ接続。remote bindingsと `--remote` は使用しない。
5. 専用ブラウザプロファイルとダミーlocalStorage。普段のブラウザの保存データは使用しない。
6. 検証先は `127.0.0.1` の指定ポートに限定。クロスオリジン検証用に別ポートを用意する。必要ならhost-onlyネットワークの専用VMを使い、公開IPへは公開しない。
7. HTTP試験ツールとブラウザ双方で外向き通信を遮断。リダイレクト先にも許可先チェックを適用し、X・YouTubeはローカルの代替応答を使うか読み込みを遮断する。
8. ツール取得が必要な場合は検証開始前に分離して行い、バージョンを固定・記録する。検証中は外部通信しない。

確認した環境: Node.js v22.14.0、npm 10.9.2あり。WranglerはPATH上に見当たらず、導入・動作確認が必要。Docker CLIはあるがエンジン稼働は未確認。Dockerは必須ではない。

## 現時点の確認事項と検証候補

| 優先度 | 対象 | ソース上の事実 | 検証すること |
| --- | --- | --- | --- |
| 低 | 閲覧数API | アプリ内に回数制限・認証なし。Origin等がない要求を許容する | 少数の反復要求で任意に加算できるか。集計汚染・DB呼び出し増加の条件。匿名カウンターの仕様と問題を区別する |
| 中 | Origin判定 | Originが存在すれば一致判定。Sec-Fetch-Siteにも判定あり | 別Origin、null、ヘッダー欠落、同一サイト別Origin、各HTTPメソッドの処理とDB非更新を確認。認証付き操作のCSRFとは区別する |
| 高 | 環境の分離 | 配置手順92行にProductionとPreviewで同じD1バインディングを使う記載 | 既存Previewを検証に使わない。実際のクラウド設定は未確認。本番DBへ接続できない構成を先に確認する |
| 中 | 成長率の描画 | `growth.js` にinnerHTMLあり。通常のデータは固定カタログから取得 | 保存データ・ドラッグ入力から任意文字列がHTMLに到達するか。innerHTMLの存在だけでXSSと認定しない |
| 中 | 成長率のドラッグ | sourceSlotの整数判定はあるが、参照前の範囲チェックが見当たらない | 範囲外番号、別カテゴリの既知ID、不正JSONで例外・状態破壊が生じるか。外部からの到達可能性と自己改変を区別する |
| 中 | localStorage | 複数ページでJSON読込・保存。成長率の保存には例外処理がない | 壊れたJSON、未知ID、型違い、数値上限、容量不足、保存拒否から復旧できるか。他利用者へ波及する問題とは区別する |
| 高 | URL・外部埋め込み | 検証記録はHTTPSとホスト許可リスト、textContentを利用。Xのスクリプトを直接読み込む | URL偽装・危険スキームを拒否するか。外部スクリプトが同じOriginの保存データにアクセスできる信頼境界を記録する。アクセス能力だけで実際に漏えいしたとは認定しない |
| 高 | 公開範囲 | `dist/` を配信する設計 | `.git`、設定、SQL、文書、退避画像、パストラバーサル経由で非公開ファイルの内容が返らないこと。200のHTMLフォールバックと漏えいを区別する |
| 中 | セキュリティヘッダー | リポジトリに `_headers` やCSP設定は見当たらない | CSP、frame-ancestors、nosniff、Referrer-Policy等の有無と挙動。Cloudflare側設定がないとは断定しない |
| 高 | SQL・障害応答 | SQLは固定文字列で、利用者入力を連結していない。失敗時は一般的なエラー本文 | DB内容、秘密マーカー、スタック、内部パスが応答へ漏れないことを優先。本文・クエリがSQLへ混入しないことも確認。明確なSQLインジェクション経路は未発見 |

## 実施順と上限

上記「最優先の調査手順」の静的調査を先に完了し、その後に以下のローカル検証へ進む。負荷試験は情報漏えいの確認に必要な場合だけ行う。

1. 検証コピー、固定ツール、ローカルDB、専用ブラウザを準備する。
2. 接続先許可リストと外向き遮断を確認し、正常操作の基準結果を保存する。
3. NodeによるAPI・入力処理の単体試験、既存テストを実行する。
4. ローカルPages環境でHTTPメソッド、Origin、ファイル公開範囲、ヘッダー、APIの反復呼び出しを確認する。
5. ブラウザでDOM、ドラッグ、保存データ、iframeを使ったUI誘導への耐性を確認する。XSSの検証印は専用画面内の無害なマーカーとし、データ送信は行わない。
6. 初回HTTP試験は全体300要求以内、最大同時5、毎秒10要求以内、反復試験60秒以内を上限とする。停止不能なループや飽和攻撃は行わない。
7. 外部通信の試行、予期しないプロセス停止、ローカルDB以外へのアクセス、リソース異常があれば停止し記録する。
8. 修正候補をまとめ、修正後は同じ条件で再検証する。今回の要件調査ではアプリの修正・デプロイは行わない。

## 報告・完了条件

- ケースごとに入力条件、期待値、実測、再現手順、ログ、対象コミットを記録する。
- 報告には露出経路（配信・Git・API・外部通信）、閲覧できる主体、情報の種類、現在か過去かを添える。実秘密や個人情報の生値は載せない。
- 原本が必要な証跡は公開フォルダとGit管理外に限定する。Git管理する要件書・報告書には伏せ字と再現用の架空値だけを使う。
- 脆弱性、堅牢性の不具合、仕様上許容する挙動、未検証項目を分ける。
- 深刻度は第三者による到達可能性、必要な利用者操作、影響範囲に基づき付ける。自己のlocalStorageを書き換えただけで遠隔攻撃と評価しない。
- 本番・第三者サービスへの検証通信がないこと、元データが保たれていることを確認する。
- ローカルで再現できないCloudflareのWAF、レート制限、TLS、キャッシュ、アカウント・本番デプロイ設定は未評価として残す。
- 合格は今回の範囲で問題を再現しなかったことを意味し、脆弱性が皆無であるとの保証にはしない。
